## 1. 背景与目标

Claude Science 以本地守护进程加浏览器页面的形式运行，对话和产物保存在它自己的数据目录里。这带来两个问题：它不能和其他 agent 放在同一个界面里使用；它的数据其他 agent 不知道怎么读。

### 1.1 目标

- **G1 在 ACP 客户端中对话**：提供一个 ACP agent（下称“适配器”），让 T3 Code 等支持 ACP 的客户端可以直接和 Claude Science 对话，无需打开浏览器。
- **G2 沿用项目结构**：一个 Claude Science 项目对应一个本地文件夹，使按文件夹组织项目的客户端在侧边栏呈现“项目 → 对话”结构。
- **G3 数据可移植**：提供只读的单向导出工具（下称“导出器”），把项目、对话、产物导出为普通文件。

当前阶段只做 G1 和 G2。G3 的需求保留在 4.3，等适配器可用后再排期。

### 1.2 非目标

- 不修改 T3 Code 或 Claude Science 本身。
- 不向 Claude Science 的数据目录写入任何内容。
- 不重新实现 Claude Science 的能力（沙箱、技能、连接器、远程计算）。
- 不分发 Anthropic 的提示词、技能或其他随附资产。
- 不替代 Claude Science 的界面功能：产物渲染、标注、项目管理等仍在原界面完成。

术语见仓库根目录的 [GLOSSARY.md](../GLOSSARY.md)，代码、测试名、ticket 一律使用其中的用词。

## 3. 架构

### 3.1 结构

```
ACP 客户端（T3 Code / Zed）
        │  stdio, JSON-RPC
        ▼
  acp-agent        ACP 会话生命周期；把轮次事件翻译成 ACP 更新
        │
        ▼
  science-daemon   登录、发消息、订阅流式事件、取消
        │  HTTP + WebSocket（仅回环地址）
        ▼
  Claude Science 守护进程

  project-link     读写“文件夹 ↔ 项目”的标记文件
  cli              命令行：acp、projects、link、doctor
```

### 3.2 深模块

每个包是一个**深模块**：接口小，实现藏在后面。

```
src/
  main.ts                 进程入口，只负责把标准输入输出和环境交给 cli 包
  packages/
    <包名>/
      index.ts            入口文件：包的公开接口
      testing.ts          可选的第二个入口：供测试使用的替身
      lib/                实现，包外不可引用
      tests/              测试，只能通过入口文件使用包
```

规则由 dependency-cruiser 强制，违反即 CI 失败：包外代码只能引用包根目录下的入口文件；测试也只能通过入口文件；不允许循环依赖。不写把整个子目录重新导出的 barrel 文件。

| 包               | 接口（入口文件对外提供的能力）                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------------- |
| `science-daemon` | 连接守护进程；列出项目；发起对话并发送消息；以异步序列给出一轮回复的事件；取消。`testing.ts` 提供假守护进程。 |
| `acp-agent`      | 给定“如何连接守护进程”的函数，构造 ACP agent。项目通过 `project-link` 包按会话的工作目录查找。                |
| `project-link`   | 从某个目录向上查找标记文件；把一个目录关联到项目。                                                            |
| `cli`            | 给定参数与进程环境（标准输入输出、环境变量、工作目录），运行一条命令并返回退出码。                            |
| `folder-names`   | 给定一组项目，为每个项目给出跨平台安全且互不相同的文件夹名。                                                  |

设计约束：

- `acp-agent` 不直接发 HTTP 请求；`science-daemon` 不引用 ACP 的任何类型。
- 与守护进程接口有关的全部知识集中在 `science-daemon` 与 `protocol.md`，接口变化时只改这两处。
- 依赖通过参数传入，不使用模块级可变状态。
- 不为“将来可能需要”预留抽象：只有当接缝两侧确实存在两种实现时才引入接口。

### 3.3 标记文件

位置：`<项目文件夹>/.csbridge/project.json`。目录名特意不用 `.claude-science`，避免与 Claude Science 自己位于用户主目录下的数据目录同名。

```json
{
  "schemaVersion": 1,
  "projectId": "proj_xxxxxxxxxxxx",
  "name": "项目名",
  "linkedAt": "2026-11-15T08:00:00Z"
}
```

从工作目录开始逐级向上查找，取最近的一个。`schemaVersion` 不认识时报错。

### 4.4 导入已有对话

T3 Code 把这项能力称为“原生会话”（native sessions），其行为读自 T3 Code 的程序代码，尚未在界面上实测：

- **探测**：T3 启动适配器并新建一个会话来读取能力。因此 `session/new` 不能因为目录未关联而失败。
- **列出**：适配器声明 `sessionCapabilities.list` 后，T3 以某个项目的文件夹为 `cwd` 调用 `session/list`，取每个会话的标识、标题、更新时间，每页最多 256 个。
- **导入**：适配器声明 `loadSession` 后，用户在 provider 设置的 “Native sessions” 里选择会话，T3 为它建一个线程。已导入的会话由 T3 按会话标识识别。
- **加载**：打开线程时 T3 调用 `session/load`，适配器在应答之前把历史逐条以会话更新的形式发回，T3 据此填充线程内容。T3 重启后对已有线程也调用 `session/load`。

由此得到的设计：

- 列出与加载时，会话标识就是对话标识。
- 客户端新建的会话在对话存在之前就要有标识，所以适配器在自己的状态目录（`CSBRIDGE_STATE_DIR`，默认 `~/.csbridge`）里记录“会话 → 对话”的对应关系。这份记录不含消息内容，不写入 Claude Science 的数据目录。已有对应关系的对话不再列出，避免重复导入。
- 层级结构：一个 Claude Science 项目对应一个已关联的文件夹，文件夹作为客户端的项目，项目下的对话作为线程。`csbridge link --all` 一次建好全部文件夹；把文件夹加为客户端的项目由用户完成。
- 历史以文本回放：用户输入、回复正文、工具调用（标题）。守护进程注入的消息不回放。
- 对应关系记录在状态目录的 `sessions.jsonl` 里，每行一对标识，只追加不改写，多个适配器进程同时写入也安全。
- **实测结论**：T3 Code 在 `session/load` 期间会丢弃适配器回放的全部历史，只用这次加载恢复 agent 一侧的上下文，所以导入的线程打开时是空的。为此适配器提供 `/history` 命令：把对话历史整理成回复文本显示在线程里，不向 Claude Science 发送任何内容。

**一条命令导入（FR-M7）**。逐个手工导入不可接受：线程是空的，还会堆在“已完成”列表里。`csbridge t3-import <文件夹>` 通过 T3 Code 的命令行 `t3` 完成全部工作，不读写 T3 的数据库：

- 每个项目：建已关联的子文件夹（同 `link --all`），再用 `t3 project add` 建标题为 `CS-<项目名>` 的 T3 项目；项目已存在则沿用。前缀可用 `--prefix` 改。
- 每个还没有线程的对话：用 `t3 thread start … "/open <对话标识>"` 建一个线程，线程标题取对话标题，起始模型是 `default`（T3 对“代理自己决定模型”的称呼），`/open` 随后把它设为对话自己的模型，从旧到新，使最新的对话成为最近的线程。
- “已有线程”的判定有两个来源：状态目录里的会话记录，以及 T3 自己导入的线程（其线程标识里含对话标识）。因此命令可以反复运行，只导入新增的对话。
- `/open` 把会话绑定到对话、把历史显示在线程里，并用 `config_option_update` 把对话自己的模型与推理强度告知客户端。随后通过 T3 交给每个会话的 MCP 服务器 `t3-code` 做两件事：用 `t3_thread_configure` 把线程的模型设为对话的模型、把推理强度写成线程的选项（T3 不会从会话上报的值更新线程），再用 `t3_thread_organize` 把线程归入 settled。这两步尽力而为：没有该服务器的客户端里，`/open` 的其余行为不变。
- **T3 对换模型的限制**（实测结论）。T3 只在线程绑定着“支持切换模型”的会话时才保存换模型的操作，而线程一旦 settle 或 archive 就与会话解绑；尚未使用过的导入线程同样没有绑定会话。此时在模型菜单里选模型会提示 "This model pick was not saved. The active ACP session does not expose a model-switch capability."。因此 `/open` 必须在本轮结束之前（会话仍绑定时）设置线程的模型。读 T3 的代码可知，被拒的选择仍留在输入框的草稿里，随下一条消息一起发出并生效，此后会话重新绑定，菜单恢复正常；这一点尚未在界面上实测。
- 曾试过把模型作为普通选项（不带 `model` 类别）提供给 T3 以绕开上述限制：T3 对改选项没有限制，但模型菜单只剩一个 `Default`，真实模型要到二级分栏里选，使用者不接受，已弃用。该做法在线程上留下过标识为 `model` 的选项；T3 会在应用线程的模型之后再逐项应用选项，同名选项会覆盖用户选的模型，所以模型选项的标识改为 `claude_science_model`，使残留的选项不再被应用。
- 某个对话导入失败不影响其余对话；失败逐条写到标准错误，退出码为 1。机器上没有 `t3` 时给出说明并以 1 退出。

### 4.5 守护进程向用户提出的请求（FR-A10）

Claude Science 在一轮对话中会停下来向用户要东西：审批（访问本机文件夹、联网、执行代码等）或带选项的提问。协议细节见 `docs/protocol.md` 的 “Input requests”。

- **在客户端怎么问**。客户端在 `initialize` 里声明支持表单（ACP elicitation）时，用表单提问，选项就是请求自己的选项；否则退回 ACP 权限请求。优先用表单的原因是实测 T3 Code 对权限请求的处理：线程处于 Auto 或 Full access 模式时 T3 自己直接回答“允许”，用户看不到；其余模式也只有“同意／本次会话内同意／拒绝”三个固定按钮，按选项类别对应，表达不了“读写还是只读”“仅此一次还是本项目”。而 Claude Science 要的是用户本人的决定。表单在 T3 里总是问到用户，并显示适配器给的选项文字。
- **选项**。访问文件夹：按所请求的权限给“允许读写／允许只读／拒绝”，允许即长期有效（与 Claude Science 自己的界面一致）。其余只需是或否的审批：有“仅此一次”就给，另给 Claude Science 界面默认建议的范围（若默认就是一次，则给下一档），外加拒绝。单个单选提问：各选项加“跳过”。
- **只能在 Claude Science 里回答的请求**：要用户键入内容的（密码、密钥、邮箱等）、多个问题或多选的提问、以及不认识的种类。线程里显示一句说明，本轮继续等待；用户在 Claude Science 里回答后回复在客户端继续。密码和密钥不经过适配器与客户端。
- **流程**。一轮因请求而停下时不算结束：`science-daemon` 报告 `input-requested` 事件，回答之后同一轮继续，回复接着流式输出。用户不回答（关闭表单，或客户端报告取消）时本次 prompt 以 cancelled 结束，不向守护进程发送任何回答，请求保持未决。
- **未决请求与新消息**。守护进程在有未决请求时拒绝新消息（HTTP 400）。所以每条 prompt 发送前先看对话是否在等待回答：是则先把请求问出来，回答后把停下的那一轮接着播完，再发送新消息。
- **边角情况**。用户在客户端作答时请求已在 Claude Science 里被回答：守护进程答复 `already_resolved`，线程里说明这次选择没有生效。守护进程仍以“请先回答未决问题”拒绝新消息（例如请求来自子 agent 的帧，根帧上读不到）：以 `awaiting-answer` 报错，告诉用户去 Claude Science 回答后重发。HTTP 读到的请求列表只在对话处于等待或运行状态时才算数，回答发往持有列表的那个帧。T3 只对带 Codex 标记的表单自动作答，适配器的表单在任何权限模式下都会问到用户（读 T3 代码所得；实测过 auto-accept-edits 模式）。
- **未实测的部分**：除访问文件夹以外各种请求的字段、轮次仍在运行时提出的请求、子 agent 帧提出的请求、取消对已停下的一轮的作用。代码对前三者有处理但只有假守护进程上的测试。

### 4.3 导出器（暂缓）

只读、单向地把项目、对话、产物导出为“每个项目一个文件夹、对话为 Markdown、产物为原文件”。要求：数据库只读打开；只读取允许清单内的表；幂等且增量；只管理自己创建的文件；文件名跨平台安全；数据库结构不符时明确报错。排期前另行细化为 ticket。

## 5. 非功能需求

### 5.1 代码质量

- **NFR-Q1** `pnpm check` 全部通过：类型检查（严格模式，含 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`）、Biome、模块边界、测试。不用 `any`，不用类型断言绕过检查；确需例外时注明原因。
- **NFR-Q2** 来自外部的数据（守护进程响应、标记文件、命令行输出）在进入内部类型之前先校验结构。
- **NFR-Q3** 错误使用带类别的错误类型；不吞异常；面向用户的错误说明原因和下一步操作。
- **NFR-Q4** 修复缺陷必须附带能复现该缺陷的测试。

### 5.2 可移植性

- **NFR-P1** 支持 macOS 与 Linux，二者均在 CI 中测试。不使用仅限某一平台的接口，使 Windows 不被代码结构排除，但不作为已测试平台。
- **NFR-P2** 不写死任何路径、端口、用户名。命令行工具依次取：命令行参数、环境变量 `CLAUDE_SCIENCE_BIN`、`PATH`、默认数据目录下的 `bin/`。端口取自 `claude-science status`。
- **NFR-P3** 路径用 `node:path` 处理；文本读写显式指定 UTF-8；调用子进程用参数数组，不经过 shell。
- **NFR-P4** 访问守护进程时不经过系统代理。
- **NFR-P5** 安装与运行只需要 Node.js，无需编译工具链，不依赖原生模块。

### 5.3 可读性

- **NFR-R1** 入口文件导出的每个函数与类型都有说明用途和约束的文档注释，不复述代码。
- **NFR-R2** 标识符、注释、提交信息、ticket 一律用英文；命名用完整单词，并与 GLOSSARY.md 一致。
- **NFR-R3** 一个文件只做一件事，以 300 行为软上限；函数保持短小，嵌套不超过三层。
- **NFR-R4** 优先用直白的写法：不用装饰器、不用依赖注入框架、不用隐式魔法。
- **NFR-R5** 注释只解释代码本身看不出来的原因和约束。

### 5.4 安全与隐私

- **NFR-S1** 标准输出只用于 ACP 协议；日志只写到标准错误。
- **NFR-S2** 登录会话只保存在内存中；日志和错误信息中不得出现 cookie、nonce、令牌。
- **NFR-S3** 只连接回环地址上的守护进程；不发起任何其他网络请求，不收集遥测。
- **NFR-S4** 测试数据全部为合成数据；真实对话、真实项目名、真实路径不得进入仓库。
- **NFR-S5** CI 包含密钥扫描。

### 5.5 兼容性

- **NFR-C1** 代码中维护已测试的 Claude Science 版本。遇到未测试的版本时给出明确警告并继续；遇到响应结构与预期不符时明确报错，不做猜测。
- **NFR-C2** 遇到不认识的事件类型时忽略并继续，不中断会话。
- **NFR-C3** 版本号遵循语义化版本；每次发布更新 `CHANGELOG.md`。

## 6. 开发流程

流程采用 [mattpocock/skills](https://github.com/mattpocock/skills) 的工程技能，本机路径为 `~/Projects/skills/mattpocock-skills/skills/`。

| 阶段 | 技能                    | 产出                                                                        |
| ---- | ----------------------- | --------------------------------------------------------------------------- |
| 拆分 | `to-tickets`            | 一组 ticket，每个都是纵向切片，并声明被哪些 ticket 阻塞                     |
| 实现 | `implement-spec`、`tdd` | 每个 ticket 一个 worktree、一个分支；先写失败的测试，再写刚好让它通过的代码 |
| 设计 | `codebase-design`       | 深模块的统一用词，设计接口时查阅                                            |
| 评审 | `code-review`           | 从“是否符合规范”和“是否符合 ticket”两个维度分别评审                         |
| 合并 | `pr`                    | PR 描述：摘要、证据、合并风险                                               |

### 6.1 Ticket

- Ticket 发布为本仓库的 GitHub issue，约定见 `docs/agents/issue-tracker.md`。
- 每个 ticket 是一条**纵向切片**：贯穿所有层、单独可验证、能在一个全新的上下文里完成。
- Ticket 描述行为和验收标准，不写文件路径和代码片段。
- 所有阻塞项都已关闭的 ticket 构成**前沿**，前沿上的 ticket 可以同时开工。

### 6.2 分支与 worktree

- `main` 始终可发布，只通过 PR 合并。仓库起步阶段的脚手架提交除外。
- 一批相关的 ticket 共用一个**集成分支**；每个 ticket 在自己的 worktree 里从集成分支拉出分支。
- 实现者开工前确认 worktree 基于集成分支的最新提交；完成前把集成分支的最新提交合并进自己的分支并重新通过 `pnpm check`。
- 新 worktree 只包含已提交的内容，创建后运行 `pnpm install`。
- 一批 ticket 全部完成后，对集成分支做 `code-review`，修复发现的问题，再向 `main` 提 PR。
- 提交信息遵循 Conventional Commits；合并方式为 squash。

### 6.3 完成标准

- Ticket 的验收标准均有测试且通过；`pnpm check` 通过。
- 满足第 5 节的全部适用条款。
- 行为变化同步到 README 与 CHANGELOG；接口事实的变化同步到 `protocol.md`；设计决定写 ADR。
- 没有遗留的调试代码；`TODO` 必须关联 issue。

### 6.4 CI

对每个 PR 和 `main` 的每次推送运行 `pnpm check` 与 `pnpm build`，矩阵为 {Ubuntu, macOS} × {Node 22, Node 24}，另有密钥扫描。CI 不访问真实的守护进程。

## 7. 测试策略

测试只在事先约定的**接缝**上进行，通过公开接口验证行为，不测试内部实现。

| 接缝         | 测试如何使用它                                                                    | 能发现什么                           | 发现不了什么                 |
| ------------ | --------------------------------------------------------------------------------- | ------------------------------------ | ---------------------------- |
| ACP 协议     | 测试扮演 ACP 客户端，用 SDK 的客户端一侧与适配器对话，断言收到的更新和结束原因    | 适配器对外的全部行为                 | 真实客户端的界面表现         |
| 守护进程线路 | 仓库内的假守护进程，在回环地址上提供 HTTP 与 WebSocket，行为以 `protocol.md` 为准 | 登录、请求、流式事件处理是否正确     | 真实守护进程与文档不一致之处 |
| 命令行工具   | 传入一个代替 `claude-science` 的函数                                              | 状态探测、登录链接获取、各种失败情况 | 真实命令行工具的输出变化     |
| 文件系统     | 真实的临时目录                                                                    | 标记文件的读写与查找                 | 无                           |

- 首选最高的接缝：适配器的行为测试一律从 ACP 协议进入，底下接假守护进程，中间不再替换任何东西。
- 只在系统边界使用替身；不替换自己写的模块。
- 期望值来自独立的事实来源（规格、协议文档、手写的示例），不照着实现重新计算。
- 一次一个切片：一个失败的测试，一段让它通过的实现，然后下一个。
- 与真实守护进程的实测是手动步骤，发布前进行，默认不在自动测试中运行。
